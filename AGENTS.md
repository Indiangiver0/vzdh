# Правила команды «Лорд Подземелья»

## Контекст

- Общайся с пользователем по-русски, коротко объясняй изменения и их причину. Пользователь впервые работает с Git.
- Игра: средневековый бесконечный рогалик с автобоем и строительством подземелья. Godot 4.7.2, GDScript, Compatibility; проект в `auto-chess-dungeon/`.
- Перед работой прочитай относящиеся к задаче разделы `GAME_DESIGN.md` и документации игры. Последние решения пользователя важнее старых концептов; расхождения с кодом обозначай явно.
- Сохраняй основу: покупаемые этажи по пять мест, маршрут змейкой, трон последним, растущие группы героев со специализациями, способности Лорда по нажатию, души и открытия между забегами.
- Предпочитай небольшие законченные изменения. Не добавляй сервер, базу данных или общий рефакторинг без потребности задачи.

## Делегирование

- Для крупных задач делегируй независимые части профильным агентам, когда параллельная работа полезна. Простые правки выполняй самостоятельно.
- До запуска прочитай профиль нужной роли из `.codex/agents/`. Если инструмент не поддерживает выбор типа агента, передай его инструкции в задании явно: одно имя задачи профиль не загружает.
- `gameplay-balance`: `.codex/agents/gameplay-balance.toml` — симуляция, правила, герои, Лорды, экономика и данные.
- `dungeon-builder-ui`: `.codex/agents/dungeon-builder-ui.toml` — управление строительством, меню, поле, анимации и визуальная обратная связь.
- `qa-debug-polish`: `.codex/agents/qa-debug-polish.toml` — независимый разбор ошибок, проверки по запросу и доводка по отдельному заданию.
- Координатор ведёт требования, распределяет файлы, согласует интерфейсы, собирает результат и отвечает за Git/GitHub. Отдельного GitHub-агента нет.
- Одновременно используй не более трёх подагентов и доступного лимита среды. Подагенты не создают других агентов.

## Работа с общими файлами

- До делегирования укажи каждому цель, разрешённые файлы, ожидаемый результат, зависимости и разрешены ли проверки. Список владельцев держи в плане текущей задачи.
- Один файл одновременно изменяет один исполнитель, включая координатора. Зоны ролей — исходное распределение; точный список файлов в задании имеет приоритет.
- Gameplay обычно владеет `dungeon_game.gd`, каталогами, `lord_progression.gd`, `scripts/definitions/` и `data/` внутри проекта Godot.
- Builder/UI обычно владеет `main.gd`, `dungeon_view.gd`, `scenes/` и `assets/`. `project.godot` изменяет только назначенный исполнитель.
- `main.gd` содержит также сохранения и управление забегом. Для изменения наград или профиля сначала согласуй с Gameplay схему данных и порядок вызовов.
- QA может читать весь проект; тесты и исправления пишет только в явно выделенные файлы. Проверку результата начинай после завершения соответствующих правок.
- Если нужен чужой файл, сообщи координатору требуемую правку и продолжай независимую часть. Координатор передаёт файл после завершения работы его владельца.
- В общем checkout подагенты не переключают ветки, не делают stash, commit, merge или push. Не отменяй чужие изменения.

## Реализация и проверка

- Игровые правила и расчёты остаются в модели; интерфейс вызывает её действия и отображает реальные значения. Отрисовка не меняет исход боя.
- Сохраняй детерминированность при фиксированном seed, стабильные ID ресурсов и совместимость профилей. Награду за забег начисляй однократно.
- Не меняй личные `user://`-сохранения для отладки. Используй изолированные данные; логи и снимки помещай в игнорируемую `auto-chess-dungeon/artifacts/`.
- Добавляй и запускай тесты только по запросу пользователя на тестирование или проверку. Делегирование QA само по себе не даёт такого разрешения; передай ему существующий запрос пользователя.
- Команды и покрытие: `auto-chess-dungeon/tests/README.md`. Исторические результаты не считай проверкой текущих изменений; headless-проверка не подтверждает внешний вид.
- Отчёт агента: что сделано, изменённые файлы, изменения интерфейсов/данных, выполненные проверки с результатами или «не запускались», оставшиеся риски и передача следующему исполнителю.

## Git и завершение

- Перед изменениями посмотри `git status`; сохраняй незавершённую работу пользователя. Для новой крупной задачи создай `codex/<task>` от подходящей актуальной базы; существующую ветку задачи продолжай.
- Коммиты: `<тип>(<область>): <краткое описание на английском в повелительном наклонении>`, без точки. Пример: `feat(agents): configure dungeon development roles`.
- Git-операции выполняет координатор в рамках запроса пользователя. Не переписывай опубликованную историю, не удаляй ветки и stash без отдельной причины и авторизации. Версии отмечай тегами при выпуске.
- При создании PR используй русские разделы «### 📝 Что сделано», «### ⚙️ Как это работает / Технические детали», «### 🧪 Как протестировать».
- Перед завершением просмотри общий diff и статус. Сообщи пользователю, что изменено, что проверено, текущую ветку и сохранены ли изменения коммитом / отправлены ли на GitHub.
